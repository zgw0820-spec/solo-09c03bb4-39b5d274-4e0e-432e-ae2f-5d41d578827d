# 机房设备校时前诊断

值班员在给设备校时前，用本系统核对**诊断机相对两台内网 NTP 时间源的钟差**
是否在容许范围内。网页上可实时调整两源的钟差与回包延迟，填写容许偏差后
发起**真实 UDP 探测**，系统按本轮 NTP 请求/回应的四个时间戳计算各源钟差
及网络延迟引入的不确定区间，给出四态判定。

探测超时时，网页还会显示**链路追踪**：按本轮请求标识到各源控制口查询
收包 / 发包记录，逐源说明请求在哪个环节失去响应（源未见请求、源已收包
但尚未发出、源已发包但诊断机未收到等）。控制口不可达、源在探测期间重启
或记录过期时只报“证据不足”，不据此断定网络丢包。

## 组成

| 服务 | 说明 | 端口 |
|---|---|---|
| `diag` | FastAPI 诊断服务：操作网页 + REST API + UDP 探测 | 8000 (HTTP) |
| `ntp1` / `ntp2` | 本地 NTP 时间源：UDP 应答 + HTTP 控制口（调钟差/回包延迟） | 123/udp、9000 (控制口) |

```
┌────────┐  HTTP 配置   ┌──────────────┐
│ 浏览器  │ ◄──────────► │    diag      │ ──UDP NTP 探测──► ntp1 (源1)
└────────┘              │  FastAPI     │ ──UDP NTP 探测──► ntp2 (源2)
                        └──────┬───────┘
                               │ HTTP（控制口 9000）实时调整
                               ▼
                        ntp1 / ntp2 的 offset_ms、reply_delay_ms
```

## 判定逻辑

对每台源取一轮四时间戳：t1 本机发送、t2 源接收、t3 源发送、t4 本机接收。

- 钟差点估计 `θ = ((t2-t1)+(t3-t4))/2`
- 往返网络时延 `δ = (t4-t1)-(t3-t2)`
- 真实钟差的不确定区间 `[θ-δ/2, θ+δ/2]`（由 `|θ-θ*| ≤ (d去+d回)/2` 推出）

综合两源区间与容许偏差 `±tol`：

| 条件 | 判定 |
|---|---|
| 任一源超时 / 回包无效 / 迟到串包 | **无法判断** |
| 两源区间不相交（互相矛盾） | **无法判断** |
| 交集 ⊆ [-tol, +tol] | **无需校时** |
| 交集 ∩ [-tol, +tol] = ∅ | **需要校时** |
| 交集跨越 ±tol 边界 | **待核**（人工复核或重测） |

## 回包校验（无效/迟到拒绝）

- 报文不足 48 字节、mode≠4（非服务器应答）、stratum 不在 1..15 → 拒绝
- originate 时间戳与本轮请求的 t1 不符（迟到/串包）→ 拒绝
- t3<t2、往返为负、推算网络时延为负、往返超过超时 → 拒绝
- 超时未收到应答 → 该源判失败

## 并发不串包

- 每次诊断为每个源**新建独立 UDP socket**（内核分配临时端口，用完即关），
  请求之间无共享状态，内核按四元组投递，物理上不会串包；
- 回包必须原样回显本轮 t1（含微秒级小数），对不上即拒收；
- 超时后到达的迟到包随 socket 关闭被内核丢弃；
- 源端为无状态应答器，每个数据报独立任务处理，互不干扰；
- 链路追踪同样按轮隔离：每轮每源各生成一个 16 位十六进制请求标识，
  源端按该标识登记记录，诊断端只采信 originate 与本轮 t1 完全一致的
  那一条，绝不借用别轮或他源的记录。

## 链路追踪

请求在标准 48 字节 NTP 报文后追加 16 字节扩展区（16 位十六进制请求
标识，标准 NTP 源会忽略）。源端收到请求时登记“已收包”，真正调用
`sendto` 前补记“已发包”；诊断端探测结束后用**本轮标识**查询
`GET /trace/{标识}`。逐源给出以下状态：

| 状态 | 含义 | 结论性 |
|---|---|---|
| 源已发包且诊断机按时收到 | 全链路正常 | 是 |
| 源端查无本轮请求记录 | 请求未到达源端（去程、端口/地址错误或源未启用追踪） | 是 |
| 源已收包但尚未发出 | 源端收到请求，查询时应答仍在回包延迟中 | 是 |
| 源已发包但诊断机未按时收到 | 问题在回程链路或诊断机收包环节 | 是 |
| 源已发包，诊断机迟到/串包拒收 | 回包超出超时或 originate 不符 | 是 |
| 源已发包，诊断机收到但回包无效 | 格式/模式/时间戳校验未通过 | 是 |
| **证据不足** | 控制口不可达 / 源在探测期间重启 / 记录过期 / 查不到与本轮 t1 对应的记录 / 证据自相矛盾 | **否，不得据此断定丢包** |

探测前后各读一次源端 `GET /health` 的 `boot_id`（每次进程启动随机生成）。
两次不一致即判定源在探测期间重启，重启前后的记录不可互相印证。
记录有效期由源端 `TRACE_TTL_S`（默认 120 s）控制，过期后查询返回
`expired`，仍能说明“源曾见过该标识”，但不再作为本轮证据。控制口查询
失败不会影响 UDP 探测本身与四态判定。

网页对每个源显示“发出请求 → 源端收包 → 源端发包 → 诊断机收包”四步
时间线与结论徽标；超时源可点“重新查询本记录”再查一次（仍只用本轮标识，
判定不因重查而改变）。

## 回包延迟的模拟方式

源端在收到请求时即给 t3 盖章，随后让应答包滞留 `reply_delay_ms` 再发出，
使延迟体现为**回程网络时延**而进入 δ，从而拉宽不确定区间（若先睡眠再盖
t3，延迟会被当作服务器处理时间从 δ 中扣除，失去模拟意义）。把延迟调到
超过探测超时即可模拟源超时。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 操作网页 |
| GET | `/api/sources` | 两源当前配置（实时取自源端控制口） |
| POST | `/api/sources/{1,2}/config` | 调整 `offset_ms` / `reply_delay_ms` |
| POST | `/api/diagnose` |  body：`tolerance_ms`、`timeout_ms`；返回四时间戳、θ、δ、区间、交集、四态判定，以及每源的 `links` 链路追踪状态与 `round_id` |
| POST | `/api/trace` | body：`round_id`、`source_id`；按该轮本轮标识重查源端收发记录（不改变判定） |
| GET | `/api/health` | 健康检查 |

源端控制口：`GET/POST /config`、`GET /health`（含 `boot_id`）、
`GET /trace/{请求标识}`（端口 9000）。

## 已知限制

- 时间源为教学用模拟实现（stratum=2，时钟即容器系统时钟 + 配置偏移），
  不实现完整 NTP 服务的时钟驯服；真实部署可替换为 chrony/ntpd 容器，
  诊断端无需改动。**但真实 chrony/ntpd 不会回显追踪扩展、也不提供
  `/trace` 控制口**——对这类源，链路追踪会如实显示“控制口不可达 →
  证据不足”，不会伪造结论；四时间戳判定不受影响。
- 链路追踪记录仅存于源端进程内存，源端不提供粘滞会话或持久化；高负载
  下超过 `TRACE_MAX_ENTRIES` 的最旧记录会被淘汰（查询显示 `not_found`）。
- 单容器单事件循环，延迟模拟精度受宿主机调度影响（毫秒级）。
